## 対応内容

### `reward.ts` — 報酬の分解と観測状態

合成報酬は保存しない。生イベントを記録し、重みは設定で後から変える。一度
合成すると、重みを変えたときに過去のログが使えなくなる。

- 同じ種類のイベントが複数回あっても 1 回ぶん。誤タップで 2 回押した記事の
  報酬が 2 倍になるのはおかしい
- 未操作の impression は 0。**罰にしない**（押されなかったことは観測ではない）
- `no_click` というイベントは型にも存在しない

`finalizeObservation` が §6.3 の中核。

- **通過証明** — 自分に `viewed` が無くても、より下位のカードに `viewed` が
  あれば視界には入っている。ここを落とすと、速く読む人の記事がまとめて
  「見ていない」扱いになり、ペアの母集団が不当に小さくなる
- 最後に `viewed` されたカードより下は `examined = false`。ここを甘くすると、
  見えていない記事が比較対象に入って**偽の負例**になる

### `rewardJoinWorker`

順序が意味を持つ。`examined` を先に確定しないと、ドメインの `examinedCount`
が実際より少なくなり、降格も昇格も判定がずれる。

1. 昨日以前の Briefing の観測状態と `examined` を確定（当日ぶんは触らない。
   まだ見るかもしれない Briefing を `unobserved` に固めると、その日のログが
   丸ごと学習から落ちる）
2. 読了・ハイライト・お気に入りを遅延報酬として join（観測窓 7 日）
3. 窓を過ぎた impression の報酬を確定。確定後は更新しない
4. ドメインとクラスタのカウントを実ログから引き直す

カウントは差分更新ではなく毎回集計し直している。差分にすると、イベントの
取り消しや再提示で少しずつずれ、**ずれたことに誰も気づけない**。

`requeueUnobserved` は未観測 Briefing の上位 5 件を候補に戻すだけにして、
実際の提示は rankWorker に任せる。新しい impression として記録する必要が
あり、元の impression は未ラベルのまま残す必要があるため。

## 見つけた不具合: 相関サブクエリが黙って 0 を返す

疎通確認で `examinedMarked: 0` と `positive: 0` になり、掘ったら同じ原因
だった。

drizzle の `sql` テンプレートに書いた相関サブクエリ

```sql
(select count(*) from recFeedbackEvents
 where recFeedbackEvents.impressionId = recImpressions.id ...)
```

が常に 0 を返していた。**例外は出ない。** 結果として、

- `examined` が 1 件も立たない → 学習に使えるログがゼロになる
- ドメインの事後分布が事前値（0.2）に張り付く → 昇格も降格も永久に起きない

どちらも「何も起きない」形で失敗するので、動かしてみるまで気づけない。
素直に 2 本のクエリに分けて JS で突き合わせる形に直した。1 人ぶんのログなら
全件引いても一瞬で終わる。

**このバグは Phase 1 の完了条件をすべて静かに無効化する種類のもの**だった。
「毎朝 Briefing が出る」までは動いて見えるのに、学習データが 1 件も貯まらない。
