## なぜ方式を変えたのか

外部プロバイダ経路は HTML チャンクを丸ごと渡し、「タグを一字一句変えるな」と
指示して出力を検証している。**ローカルの 4B 級はこれが通らない。** 実測:

| モデル | HTML を渡したときの挙動 |
|---|---|
| translategemma:4b | 散文は通るが、コードを含む章で 91 タグ → 16 タグに崩壊 |
| qwen3.5:4b | 2 チャンク中 1 つで原文をそのままエコー |
| CAT-Translate-3.3b | **翻訳ではなく命令を実行した**。`<code>rustup</code>` を含む段落を渡したら `<code>rustup install 1.90.0</code>` が返ってきた |

素テキストの訳質は CAT が最良だったので、**モデルには素テキストしか見せない**
方針にした。構造の保存が「モデルへのお願い」から**コードの不変条件**になる。

## 実測（Rust 1.90 リリースノート 2 チャンク / CAT-Translate-3.3b / n1 GTX 1650）

```
chunk 1: 3541 chars, 13 blocks, 102 tags → 43.0s
         tags 102 → 102  順序も完全一致  findChunkProblems 0 件
         訳出 8 / 失敗 2 / タグ復元不可 3
chunk 2: 2724 chars, 20 blocks, 108 tags →  5.0s
         tags 108 → 108  順序も完全一致  findChunkProblems 0 件
         訳出 6 / スキップ 13（API 名だけのリスト項目）/ タグ復元不可 1
```

**構造は完全**。訳出は段落 13 個中 8 個で、残りは原文が残る。

原文が残った 5 個の内訳:

- 3 個 … 文中リンクが 3 つ以上あり、プレースホルダを元どおり戻せなかった
- 2 個 … 検証で弾いた。`LLD is now the default linker on [0]` に対して
  **`LLD 1.25は、…` という存在しない版番号を捏造**、別の段落では
  `. . . . .` に発散した

## 設計上の判断

### ブロック単位。テキストノード単位ではない

最初はテキストノード 1 つずつ訳す実装にした。構造は同じく完全に保たれるが、
**出力が明確に悪くなった**: 文の断片を単独で渡すと、モデルが
「1987年」「1つ選んでチェックしてください」のような接続詞ごとの捏造を返し、
同じ段落に日本語と英語が混ざる。段落まるごと英語で残るほうが読者にとって
害が少ないので、この案は採らなかった（実装も消した）。

### プレースホルダの順序は問わない。入れ子だけ検査する

順序の完全一致を求めると取りこぼしが多すぎた。日本語は英語と語順が違うので、
`<a>` で囲まれた句が文中で移動するのは**正しい翻訳の結果**であって失敗では
ない。一方、開きタグと閉じタグが入れ替わると入れ子が壊れるので、
`isWellNested()` で実際に検査して弾く。

### 全角括弧は責めずに戻す

日本語に訳すとモデルは `[0]` を `【0】` に直してくる。訳としては自然なので、
`normalizePlaceholders()` で戻してから照合する。

### 文中の `<code>` は中身ごと隠す

中身を見せると `found` → 「見つかりました」、`True` → 「真」と訳す。実測では
**再サンプリングしても毎回起きる**（`restoreCodeContent` がある理由と同じ）ので、
そもそも見せない。

### 訳せないときは原文を残す

「訳せた箇所は正しい / 訳せない箇所は原文が残る」に倒してある。捏造された
日本語が混ざるより、英語が残るほうが害が少ない。ガードは 3 つ:

1. 原文の 3 倍を超える長さ → 却下（発散）
2. 日本語が 5% 未満 → 却下（訳したつもりで英語のまま）
3. 40 字未満の断片で、原文に無い数字が出た → 却下（版番号の捏造）

## 残課題

- **既定は `external` のまま。** 全文をきれいに訳したいなら大きいモデルを使う
- 文中リンクが多い段落の訳出率を上げる余地はある。プレースホルダを
  `<0>…</0>` の対にする案も試したが、CAT は対の片方だけ返すことがあり
  改善しなかった
- 速度は 3.5KB のチャンクで 43 秒（外部経路は ~7 秒）。GPU を
  worker-3 に passthrough するか vLLM に載せ替えるかは別途
