## 何が起きたか

giken-cluster の 05:30 の実行で、**10 件のバッチが 1 件も読めず単発 10 回に
落ちた**。前日にも同じことが 1 回あった (計 2 回)。

前日に入れた debug ログを見ると、応答は素直な形で始まっていた。

```
unparsable batch response: {
  "items": [
    { "id": 1, "title_ja": "HTTP経由でファイルを提供する3つの方法…
```

先頭 300 字しか出していなかったので確定はできないが、**途中で切れた JSON**
なら説明がつく。`{` から最後の `}` までを切り出す実装では、外側が閉じて
いない応答は丸ごとパースに失敗する。中の項目は完全な形で入っているのに、
1 件も拾えない。

## 直し方

全体が読めなかったときだけ、文字列中の「対応が取れている `{...}`」を
すべて読んで項目を拾う。入れ子の内側から閉じるので、外側が閉じていなくても
中の項目は取れる。文字列リテラル内の `{}` と `\"` は状態を持って読み飛ばす。

**ID を持つ項目しか拾わない。** 通常経路では「配列の位置 + 1」で ID を
補えるが、途中で切れた応答では何件目まで来ているのか保証が無い。位置で
補うと別の記事の要約を書き込みかねないので、ID が無ければ諦めて単発の
作り直しに回す。

今朝のケースなら、単発 10 回が 1 回で済んでいた計算になる。

## ログを足した

- バッチ 0 件: 長さと**末尾**も出す。先頭だけだと「途中で切れたのか、最初から
  別の形なのか」が判別できない
- 単発が読めなかったとき: 今までは例外でなければ何も残らず、実際に
  `digestStatus=failure` が 1 件出たのに理由を追えなかった
