# test(e2e): ワーカー待ちのタイムアウトを 120 秒にする

- 作業日時: 2026-08-07
- 対応内容:
  - E2E のタイムアウトを 60 秒 → 120 秒に引き上げた。
- 変更したファイル:
  - `packages/e2e_tests/vitest.config.ts`
  - `packages/e2e_tests/utils/general.ts`
  - `docs/briefing/devlog/2026-08-07-e2e-timeout.md`

## 背景

Node 24.19.0 の abort（`2026-08-07-e2e-node-2419-abort.md`）を潰したあとに
残った不安定さ。CI run 31208679620 では

- コンテナは完全に正常（`Assertion failed` 0 件、ワーカーの起動 1 回のみ、
  `s6-rc: warning` 0 件）
- 落ちたのは `import.test.ts > should import 15 bookmarks of different types`
  の 60 秒タイムアウト 1 件のみ

だった。ログを見るとインポート自体は**成功している**。

```
18:59:07  [import] Claimed batch of 10 items ...
18:59:13  [import] 5 item(s) finished downstream processing (5 succeeded, 0 failed)
19:00:15  [import] 7 item(s) finished downstream processing (7 succeeded, 0 failed)
19:00:15  [import] Session oit0zmk3ygyad8t7usoyi2c6 completed, all items processed
```

68 秒かかっている。19 個のテストファイルが 1 つのコンテナを共有して並列に
走るため、クローラの 6 ワーカーの取り合いになり、処理待ちが他ファイルの負荷
次第で大きく振れる。4 コアの CI ランナーでは 60 秒に収まらないことがある。

つまり**アサーションが間違っているのではなく、待ち時間の予算が足りない**。
このタイプの失敗は base ブランチでも起きていて（run 31186396917 は
`bookmarks.test.ts` の 4 件、run 31185145768 は `inference.test.ts` の 2 件が
それぞれタイムアウト）、毎回違うテストが落ちる。並列実行の負荷分布で
どれが割を食うかが変わるだけ。

## 対応

`vitest.config.ts` の `testTimeout` と `utils/general.ts` の `waitUntil` の
既定値を 120 秒に揃えた。テスト内の `waitUntil` 呼び出し 21 箇所はすべて
既定値を使っているので、この 2 箇所で足りる。

pass するテストの実行時間は変わらない。本当にハングした場合の検知が
60 秒遅くなるのは許容する。

## 検討して採らなかった案

- **並列度を下げる**（`fileParallelism: false`）: 574 秒の run のうち 414 秒が
  テスト実行なので、直列化すると CI が大幅に長くなる。
- **`CRAWLER_NUM_WORKERS` を増やす**: ランナーは 4 コアで、実質 Chrome が
  CPU を食っている。ワーカーを増やしても待ち行列が短くなるとは限らない。

## 確認内容

- CI を複数回まわしてタイムアウト失敗が出ないこと。

## 残課題

- `video.test.ts > downloads a video attachment using yt-dlp` は実ネットワーク
  から動画を取得するため、回線が細い環境では落ちる（ローカルで確認）。
  CI では 39.7 秒で pass しているので今回は触っていない。
