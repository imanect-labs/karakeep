# fix(docker): Node を 24.18 に固定して better-sqlite3 の abort を止める

- 作業日時: 2026-08-07
- 対応内容:
  - E2E が不安定な真因を特定し、Node のバージョンを 24.18 に固定した。
- 変更したファイル:
  - `docker/Dockerfile`
  - `tooling/github/setup/action.yml`
  - `.nvmrc`
  - `packages/db/drizzle.ts`（コメント修正のみ）
  - `packages/db/migrate.ts`（コメント修正のみ）
  - `apps/workers/index.ts`（コメント修正のみ）
  - `docs/briefing/devlog/2026-08-07-e2e-node-2419-abort.md`

## 真因

Node **24.19.0** で `src/node_object_wrap.h` が変更され、`node::ObjectWrap` が
インスタンスごとに environment cleanup hook を登録するようになった。

```cpp
ObjectWrap() { refs_ = 0; AddCleanupHook(); }
virtual ~ObjectWrap() { RemoveCleanupHook(); ... }

void AddCleanupHook()    { AddEnvironmentCleanupHook(v8::Isolate::GetCurrent(), CleanupHook, this); }
void RemoveCleanupHook() { RemoveEnvironmentCleanupHook(v8::Isolate::GetCurrent(), CleanupHook, this); }
```

`Add/RemoveEnvironmentCleanupHook` は `src/api/hooks.cc` で

```cpp
Environment* env = Environment::GetCurrent(isolate);
CHECK_NOT_NULL(env);
```

を行う。`Environment::GetCurrent(isolate)` は**入場中のコンテキストが無いと
null を返す**。GC のウィークコールバックから走るデストラクタはまさにその状態
なので、`CHECK` が落ちて `abort()`（exit 134）する。

```
#  node[42]: void node::RemoveEnvironmentCleanupHook(...) at ../src/api/hooks.cc:142
#  Assertion failed: (env) != nullptr
 3: Statement::~Statement() [.../better_sqlite3.node]
```

better-sqlite3 の `Database` / `Statement` は `node::ObjectWrap` を継承している
ため、これを踏む。**推薦機能とは無関係の、Node 側のリグレッション**。
影響範囲は `node::ObjectWrap` を使う全てのネイティブアドオン。

## 影響

コンテナ起動時のマイグレーション（`init-db-migration`）がランダムに落ちる。

```
s6-rc: warning: unable to start service init-db-migration: command exited 134
```

これが起きると svc-web / svc-workers が起動せず、**コンテナが完全に死ぬ**。
落ちるのは `new Database()` の直後・`migrate()` の前なので、マイグレーション
自体が 1 つも走っていない（DB のテーブル数 0 で確認）。

実測（イメージ内で 20 回連続実行）:

| Node | init-db-migration の abort |
|---|---|
| 24.19.0 | 11/20、再測定で 17/20（`--max-old-space-size=4096` でも 16/20） |
| 24.18.1 | **0/20**（マイグレーション後のテーブル数 181 も確認） |

E2E が 5 割で落ちていたのはこれが理由。CI で残っていた 3 件の失敗
（`bookmarks > should search bookmarks` / `public > assets of the public bookmarks`
/ `import > should import 15 bookmarks`）はいずれも 60 秒のタイムアウトで、
ワーカーが起動直後に abort → s6 が再起動、を 13 回繰り返して最初の 80 秒を
食い潰していたことによる。

## 対応

`node:24-slim` → `node:24.18-slim` に固定。CI の `setup-node` と `.nvmrc` も
24.18 に揃えた（ユニットテストも better-sqlite3 を使うため）。

- 24.18 以前にはこの変更が無い。
- 25.x / 26.x にも無い（main には入っているので、将来 25/26 に上げる際は要確認）。
- 24.19 は現時点で 24 系の最新。修正版の 24.20 が出たら固定を外せる。

better-sqlite3 側での回避は不可。11.4 以降と 12.x は
`db.transaction(async () => ...)` を拒否する（"Transaction function cannot
return a promise"）ので、アップグレードすると trpc のテストが 243/419 落ちる。

## 誤りの訂正

これ以前の devlog（`2026-08-07-ci-branch-filter.md`）で
「`migrate.ts` が SQLite を閉じていないのが原因」と書いたが、**これは誤り**。
`closeDatabase()` を入れたイメージでも同じ確率で abort する。CI で 1 回
通ったのは偶然。`closeDatabase()` 自体は WAL チェックポイントの観点で
妥当なので残すが、コメントから誤った説明を削除した。

## 確認内容

- イメージ内でマイグレーションを 20 回連続実行 → abort **0/20**、テーブル数 181。
  （固定前は 11/20・17/20 で abort し、そのときはテーブル数 0）
- ローカルで docker compose を起動 → `Assertion failed` 0 件、
  `unable to start service` 0 件、`Workers version` 1 回のみ（再起動なし）。
  固定前は同じ操作で `unable to start service init-db-migration: command exited 134`
  が出てコンテナが死んでいた。
- CI（run 31206956365, commit 29f11aa）が全ジョブ green。
  このブランチで tests ジョブが通ったのは初めて。確率的な不具合なので
  同じコミットで rerun を重ねて確認した。
- ローカルで E2E 全体を実行 → 150/151 pass。落ちたのは
  `video.test.ts > downloads a video attachment using yt-dlp` の
  60 秒タイムアウトのみで、これは yt-dlp が実ネットワークから動画を
  取得するテスト。CI では 39.7 秒で pass しており、こちらの回線都合。
  このとき web コンテナの `Assertion failed` は 0 件、`Workers version` は
  1 回のみ。

## 残課題

- Node 24.20 でこの `CHECK` が緩和されたら固定を解除する
  （nodejs/node の `node_object_wrap.h` を確認）。
- upstream にも同じ問題があるので、報告するかどうかは別途判断。
