# Briefing Recommender

karakeep に「毎朝の記事レコメンド」機能を追加するための設計ドキュメント一式。

## これは何か

毎朝の morning briefing で「自分の興味リスト」を LLM に手渡す運用には、2 つの限界がある。

1. **リストに書いた興味でも、実際に読む記事はごく一部** — 明示した興味と実際の関心はずれる。
2. **リストに書いていない興味は永久に浮上しない** — 本人も言語化していない暗黙の関心が拾えない。

この機能は、記事の候補プールを毎日ためて、**推薦モデル**でランキングし、karakeep に 1 ページ追加した Briefing 画面で提示する。ユーザーの反応（開いた／保存した／いいねした／読み進めた／興味なしにした）を記録し、そのログでモデルを更新していく。

LLM は学習の主体ではない。**LLM はオーケストレーター、推薦モデルは意思決定器、DB は記憶**という役割分担にする。

## なぜ karakeep の中に作るのか

別サービスとして作らず、この fork の中に実装する。karakeep には既に必要な部品がほぼ揃っているため。

| 必要なもの | karakeep の既存資産 |
|---|---|
| 埋め込み生成 | `apps/workers/workers/embeddingsWorker.ts` + `InferenceClientFactory` |
| ベクトル格納 | `packages/plugins/vectorstore-meilisearch`（Meilisearch は既にクラスタで稼働） |
| ジョブキュー | `packages/plugins/queue-liteque`（SQLite ベース、追加ミドルウェア不要） |
| RSS 取得 | `apps/workers/workers/feedWorker.ts` |
| 認証 / ユーザー | NextAuth + `apiKeys` テーブル（Cloudflare Access の内側で二段構え） |
| 読了進捗 | `userReadingProgress`（`readingProgressPercent`） |
| 明示的な正例 | `bookmarks.favourited` / `highlights` / `tagsOnBookmarks` / `bookmarksInLists` |
| 記事の保存先 | ブックマーク作成 API（推薦記事の「保存」がそのまま既存機能に着地する） |
| ソース発見の材料 | `bookmarkLinks.htmlContent` / `author` / `publisher`（crawler が保存済み。追加クロールなしに外部リンクを掘れる） |
| リーダービュー | `apps/web/app/reader/[bookmarkId]`（保存後の読了計測がタダで手に入る） |
| メトリクス | workers の `/metrics`（Prometheus + Grafana は giken-ops 側で稼働中） |
| LLM 連携口 | `apps/mcp`（MCP サーバ。briefing エージェントに Tool を生やせる） |

**最大の利点はコールドスタートの解消**にある。既存のブックマーク・お気に入り・タグ・読了進捗が、初日から学習データになる。ゼロから始める独立サービスにはこれがない。

## 何を作らないか

会話ベースの構想から、1 人運用の自宅サーバーという現実に合わせて以下を削った。詳細な理由は [requirements.md](./requirements.md) の「対象外」を参照。

- **LinUCB / Neural Contextual Bandit / 本格的な強化学習** — データ量が足りない。1 日 20 件提示・年間 7,300 impression、正例は年 1,000 件程度。この規模で回せるのは正則化つきロジスティック回帰までで、それ以上は分散のほうが大きい。
- **LightGBM / Python 推論サービス** — TS モノレポに Python ランタイムを持ち込むコストに見合わない。ベイジアンロジスティック回帰は TypeScript で 200 行程度、外部依存なしで書ける。
- **収集プロンプトの自動最適化** — Phase 5 まで凍結する。推薦モデルと収集器を同時に自動更新すると、性能変化の原因が特定できなくなる。
- **毎日の LLM 検索エージェントによる候補収集** — Phase 1 では決定的なソース（RSS / HN / arXiv 等）に限定する。コストと再現性のため。ソースを広げる手段としては、まず既存データだけで動く発見チャネル（保存記事の外部リンク等）を使い切る。
- **「クリックされなかった」を負例として扱うこと** — 非クリックは観測ではない。詳細は後述の報酬設計を参照。

## モデルの段階

いきなりバンディットを回さない。データが貯まるまでは学習しても意味がないので、3 段階に分ける。

| 段階 | 中身 | 発動条件 |
|---|---|---|
| `heuristic-v1` | プロフィール埋め込みとのコサイン類似度 + 鮮度 + 多様性制約による決め打ちスコア | 初日から |
| `logreg-v1` | L2 正則化ロジスティック回帰（約 20 特徴量）を、同一 Briefing 内のペアワイズ比較で学習。ヒューリスティックスコアを 1 特徴として含む | 正例 100 件以上、かつ `examined` impression 2,000 件以上 |
| `bayes-logreg-v1` | 上記にラプラス近似で事後分散を持たせ、Thompson Sampling で探索 | `logreg-v1` がシャドー評価でヒューリスティックを上回った時 |

段階が上がる条件は自動判定し、満たさない間は下位モデルにフォールバックする。詳細は [ROADMAP.md](./ROADMAP.md) の判断ゲートを参照。

## 暗黙知を掘り出す仕組み

探索は **2 階層**で行う。記事レベルの探索だけでは足りない。

### なぜ 2 階層なのか

RSS で購読しているサイト、Hacker News、arXiv、GitHub — この母集団は自分で選んだ時点で既に**明示的な興味の写像**になっている。その中でいくらランダムに記事を選んでも、それは「自分が知っているソースの中での探索」でしかない。

本当の暗黙知は、**まだ購読していないブログや、存在すら知らないサイト**の側にある。個人ブログ、大学の研究室ページ、社内技術ブログ、ニュースレター — こうした small web は検索でもアグリゲータでも上位に来ないため、意識的に取りに行かないと永久に候補プールに入らない。

したがって、探索は次の 2 つに分ける。

| 階層 | 探索対象 | 何が広がるか |
|---|---|---|
| 記事レベル | 購読済みソース内の記事 | 既知のソース内での関心の輪郭 |
| **ソースレベル** | **候補プールを供給するドメインそのもの** | **候補の母集団そのもの** |

### 記事レベルの探索枠

| 枠 | 割合（既定） | 選び方 |
|---|---|---|
| 活用 (exploit) | 55% | 予測スコア上位 |
| 隣接 (adjacent) | 20% | 正例クラスタの近傍だが未提示のクラスタ |
| 不確実 (uncertain) | 10% | 予測分散が大きい順 |
| **試用ソース (trial)** | **10%** | **未購読ドメインの試用枠（後述）** |
| 無作為 (random) | 5% | プロフィール非依存にサンプリング |

`uncertain + trial + random` の合計 25% は設定で下回れないハードフロアとする。特に **trial 枠の 10% は、モデルがどれだけ自信を持っていても削らない**。

### ソース発見のチャネル

新しいドメインを見つける手段を、実装コストと期待値の順に並べる。既存データだけで回せるものから始める。

| ID | チャネル | 入力 | 実装コスト | フェーズ |
|---|---|---|---|---|
| D1 | **既存ブックマークのドメイン逆引き** — 手で保存したことがあるのに購読していないドメイン | `bookmarkLinks.url` | 極小 | 0 |
| D2 | **高評価記事の外部リンク抽出** — 保存した記事が繰り返しリンクするドメイン | `bookmarkLinks.htmlContent` | 小 | 1 |
| D3 | **フィード自動発見** — `<link rel="alternate">` と慣例パスの探索 | 発見済みドメイン | 小 | 1 |
| D4 | **アグリゲータのドメインサンプリング** — HN / Lobsters を「記事源」ではなく「ドメイン標本」として使う | HN / Lobsters API | 小 | 1 |
| D5 | **著者・publisher 追跡** — 高評価記事の書き手の個人サイト・他媒体 | `bookmarkLinks.author` / `publisher` | 中 | 3 |
| D6 | **blogroll 抽出** — 個人ブログのリンク集をたどる（雪だるま式） | LLM による HTML 抽出 | 中 | 3 |
| D7 | **small-web 検索** — Marginalia / searchmysite など独立サイト特化の検索 | 潜在クラスタのラベル | 小 | 3 |
| D8 | **SNS の共有リンク** — Bluesky / Mastodon でフォロー中のアカウントが共有した URL | AT Protocol / Mastodon API | 中 | 4 |
| D9 | **LLM 検索エージェント** — 未開拓トピックの Web 探索 | 潜在クラスタ + 検索 API | 大 | 5 |
| D10 | **ドメイン埋め込みの近傍** — 好きなドメインの記事重心に近い未購読ドメイン | 既存の埋め込み | 中 | 3 |

**D2 が最も費用対効果が高い**。自分が保存した記事が繰り返し参照しているドメインは、ほぼ確実に一次情報源であり、しかも被リンク回数を元記事の報酬で重み付けできる。karakeep の crawler が既に `htmlContent` を保存しているので、追加のクロールなしに今日から掘れる。

D4 の使い方は補足が要る。Hacker News の記事そのものは玉石混交だが、**上位に上がるドメインの分布**は良質な独立ブログの標本として優秀である。記事を候補に入れるのではなく、ドメインを発見器として使う。

### ドメインのライフサイクル

```
discovered ──品質ゲート──► screened ──試用枠──► trial ──昇格──► subscribed
     │                        │                   │                  │
     └──► rejected            └──► rejected       └──► rejected      ▼
                                                                  dormant ──► retired
```

- **discovered** — 発見されただけ。どのチャネルからどんな証拠で来たかを記録する
- **screened** — 品質ゲート通過。フィード URL の解決またはスクレイプ可能性を確認済み
- **trial** — 試用。最大 6 記事 / 4 週間だけ提示される
- **subscribed** — 昇格。通常の収集ソースになる
- **dormant** — 90 日更新なし、または直近 20 提示で正例ゼロ
- **rejected / retired** — 却下・退役。再発見時に再評価しないよう記録は残す

### 品質ゲート

無差別にドメインを増やすと SEO スパムとコンテンツファームで候補プールが埋まる。screened に上げる前に次を通す。

1. **ブロックリスト** — 既知のコンテンツファーム、転載アグリゲータ、パラメータ違いの重複ドメイン
2. **更新頻度** — 直近 90 日に 3 記事以上。更新の止まったサイトは trial に入れない
3. **一次情報らしさ** — 本文文字数、外部リンク比率、広告スクリプト数のヒューリスティック
4. **LLM による 1 回だけの判定** — サンプル 3 記事のタイトルと抜粋を渡して「一次情報 / 分析 / 転載 / 宣伝」に分類する。ドメインあたり 1 回きりなのでコストは無視できる

### ソースレベルのバンディット

ドメインごとにベータ事後分布 `Beta(1 + 正例数, 4 + 提示数 − 正例数)` を持ち、trial 枠のドメイン選択に Thompson Sampling を使う。

これは記事レベルより**統計効率が良い**。ドメインは数百、記事は数万。1 ドメインを 6 記事試せば、そのドメインの当たり外れは記事単位よりずっと早く判定できる。

- **昇格条件**: 提示 6 件以上、かつ事後平均が購読済みドメインの中央値を上回る
- **降格条件**: 購読済みで直近 20 提示の正例がゼロ → dormant

### 発見の可視化

Briefing ページに「今日の新しい発見」ブロックを置く。ドメイン名と**発見経路の説明**を出す。

> `simonwillison.net` — あなたが保存した記事 3 本からリンクされていました
> `some-lab.ac.jp/blog` — 「形式手法」クラスタの記事を Marginalia で検索して見つかりました

ここに **購読 / 却下** ボタンを置く。人間の一発判断はどんなモデルより安く、しかも正確である。モデルの試用判定を待たずにショートカットできる。

### 暗黙知が掘れているかの直接指標

推薦の精度が上がっても、ソースが広がっていなければ目的を達していない。次を主要 KPI にする。

- **新規ドメイン由来の保存率** — 保存した記事のうち「6 か月前には知らなかったドメイン」の割合。目標 20% 以上
- **ドメイン集中度** — 保存記事の上位 5 ドメインが占めるシェア。**上がり続けたら探索が死んでいる**
- **発見チャネル別の昇格率** — どのチャネルが効いているか。効かないチャネルは畳む

### 4 種のプロフィール

ユーザーの興味は 1 本のリストではなく、4 つのプロフィールで保持する。

- **明示プロフィール** — 手で書いたトピック（`recProfiles.explicitTopics`）
- **潜在プロフィール** — 好反応記事の埋め込み重心（長期、指数減衰なし）
- **一時プロフィール** — 直近 7 日の好反応の重心（減衰つき）
- **否定プロフィール** — 明示的に「興味なし」にした記事の重心

「本人も言語化していないが、なぜか繰り返し読む話題」は潜在プロフィールと `recClusters` の選好スコアに残る。Briefing ページの「興味の現在地」パネルで、潜在クラスタの代表記事とラベルを人間が読める形で提示する。

## フィードバックループへの対策

放置すると「似た記事を集める → 似た記事しかクリックされない → 似た記事が好きだと学習する」という自己強化ループに入る。以下を仕様として固定する。

1. **収集段階の 20% はプロフィール非依存**（固定ソースからの新着をそのまま入れる）
2. **試用ソース枠 10% を常に確保**（候補の母集団そのものを広げ続ける）
3. **記事レベルの探索枠は最低 15% を常に確保**（モデルがどれだけ自信を持っていても削らない）
4. **同一クラスタは 1 日 3 件、同一ドメインは 2 件まで**という多様性制約をランキング後に適用
5. **ドメイン集中度を監視**する。上位 5 ドメインのシェアが上がり続けたら探索が死んでいる
6. **提示されなかった候補もログに残す**（オフポリシー評価の母集団になる）
7. **推薦確率 (propensity) を保存**する。将来 IPS/SNIPS で過去ログから新モデルを評価するのに必須

## 報酬設計 — 押されなかったことを負例にしない

クリックだけを報酬にすると、扇情的なタイトルと既知の興味ばかりが強化される。報酬は合成値を保存せず、**生イベントを分解して記録**し、重みは設定ファイルで後から変えられるようにする。

```
reward = explicit_feedback      # いいね / 保存 / 興味なし
       + reading_depth          # 保存後の readingProgressPercent
       + return_behavior        # 後日の再訪・ハイライト
       + novelty_bonus          # 既存ブックマークとの非類似度
       - repetition_penalty     # 同一クラスタの連続提示
```

### 「クリックしなかった」は観測ではない

クリックしたことは安定して観測できるが、**クリックしなかったことは観測できない**。Briefing は毎日生成されるが、見ない日がある。途中までしかスクロールしない日がある。開いたが時間がなくて閉じた日がある。これらの impression をすべて負例にすると、記録されるのは興味の欠如ではなく**その日の可処分時間**になる。

対策は 3 段構えにする。

**1. 観測されていない Briefing は学習から完全に除外する**

`recBriefings` に観測状態を持たせる。`unobserved`（誰も開かなかった）/ `partial`（途中まで）/ `observed`。**`unobserved` の impression は学習データに一切入れない**。ログとしては残すが、ラベルを付けない。

**2. 実際に目に入ったカードだけを対象にする**

`observed` な Briefing の中でも、画面に入っていないカードは判断対象にしない。`examined` の判定は次のいずれか。

- そのカードが viewport に 50% 以上、1 秒以上入った（IntersectionObserver）
- **そのカードより下位のカードが `viewed` された**（通過証明。スクロールで飛ばされたが目には入っている）

最後に `viewed` されたカードより下の未到達カードは、`examined=false` として学習から外す。

**3. 明示的な負例は「興味なし」だけにする**

`examined` かつ未操作のカードを負例ラベルにはしない。代わりに、**同一 Briefing 内のペアワイズ比較**でのみ使う。

```
同じ Briefing の中で:  正例の記事 x⁺  >  examined だが未操作の記事 x⁻
学習目標:              σ(w·(x⁺ − x⁻)) を最大化
```

同一 Briefing 内で比較するので、その日の気分・可処分時間・時間帯といった日次のバイアスが**ペアの中でキャンセルされる**。しかもこれは差分ベクトルに対するロジスティック回帰そのものなので、実装は二値分類とまったく同じコードで済む（Bradley–Terry / RankNet の 1 層版）。

明示的な負例は `dismissed`（興味なし）のみ。そのため **UI では「興味なし」を押すコストを最小にする**（1 クリック、理由の入力は任意）。負例が足りないことより、偽の負例が入ることのほうが害が大きい。

### 副次的な帰結

- **クリック率の分母を変える** — 「提示数」ではなく「observed な Briefing の examined impression 数」を分母にする。そうしないと、忙しくて Briefing を見なかった週にクリック率が下がったように見えてしまう
- **見られなかった Briefing の扱い** — `unobserved` の Briefing のうちスコア上位 5 件は、翌日の Briefing に 1 回だけ再提示してよい。ただし新しい impression レコードとして記録する（同じ impression を再利用しない）
- **表示順位のバイアス** — `rank` は学習時のみ特徴量に含め、推論時は 1 位固定にすることで、「上に出たからクリックされた」分の寄与を切り離す

## デプロイ

giken-ops の ArgoCD で管理している karakeep スタックにそのまま乗る。この fork をビルドして GHCR に push し、`gitops/apps/karakeep/values.yaml` の `web.image.tag` を sha タグでピン止めする流れは既存のとおり。

推薦機能は SQLite / Meilisearch / liteque を既存インスタンスと共有するため、**新しいミドルウェアの追加は不要**。ストレージ増分は候補プール約 30 MB + 年間ログ約 50 MB を見込む。
