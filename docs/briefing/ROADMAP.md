# Briefing Recommender — ロードマップ

各フェーズは前フェーズの完了条件を満たしてから着手する。特に Phase 2 以降は**データが貯まるまで着手できない**点に注意する。実装工数より、ログの蓄積時間のほうが律速になる。

見積は自宅サーバーの個人開発（週あたり数時間）を前提とした目安。

```
Phase 0  基盤とデータ収集            2週   ── 実装律速
Phase 1  ヒューリスティック推薦 + UI    4週   ── 実装律速
Phase 1.5 ソース発見の基礎 (D2/D3/D4)  2週   ── 実装律速
              ↓ ここから 8〜12 週のログ蓄積期間
Phase 2  ペアワイズ学習              2週   ── データ律速
Phase 3  探索制御・潜在プロフィール     2週   ── データ律速
         + ソース発見の拡張 (D5〜D7/D10)
Phase 4  MCP Tool と briefing 統合    1週   ── 実装律速（Phase 1 完了後いつでも可）
         + SNS 共有リンク (D8)
Phase 5  収集戦略の最適化と OPE       3週   ── データ律速
         + LLM 検索エージェント (D9)
```

ソース発見（Phase 1.5）は**モデル学習より先**に入れる。候補の母集団が狭いまま学習を進めても、購読済みサイトの中での最適化にしかならず、暗黙知は掘れない。しかもソース発見の 3 チャネル（D2/D3/D4）は既存データと既存 API だけで動き、機械学習を必要としない。

## Phase 0 — 基盤とデータ収集

**目的**: 候補プールが毎日自動で溜まる状態を作る。推薦はまだしない。

### 作業項目

- [ ] `packages/recommender` パッケージの作成（雛形・tsconfig・turbo 登録）
- [ ] `packages/db/schema.ts` に `rec*` テーブル 9 種を追記し、マイグレーションを生成
- [ ] `recSources` の登録 UI もしくは seed スクリプト（Phase 0 では seed で十分）
- [ ] **D1: 既存ブックマークのドメイン逆引き** — 手で保存したことがあるのに購読していないドメインを `recDomains` に一括投入する。既存ライブラリだけで初期ソースプールが作れるので最優先
- [ ] `collectWorker` — RSS/Atom 収集。既存 `feedWorker` のパーサを再利用しつつ**ブックマークは作らない**
- [ ] Hacker News（Algolia API）・arXiv・GitHub Trending のソースアダプタ
- [ ] URL 正規化と重複判定（`canonicalUrl` / `urlHash`）
- [ ] **埋め込みプロバイダの分離** — `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` を追加し、埋め込み専用クライアントを作る。**これが着手の前提条件**（現状の OpenCode Go は `/embeddings` を提供しない）
- [ ] **Ollama + EmbeddingGemma-300m のデプロイ** — `gitops/apps/` に追加。requests 1Gi / limits 2Gi
- [ ] **クロスリンガル整合の検証**（下記の手順を参照）。ここで落ちたら Qwen3-Embedding-0.6B に切り替える
- [ ] `embedWorker` — 候補の埋め込み生成。入力書式は `title: {…} | text: {…}`、合計 2,048 トークン以内。`Float32Array` → BLOB のシリアライズ、**書き込み時に L2 正規化**
- [ ] `vector.ts` — 総当たりコサイン類似度（正規化済みなので内積。5,000 件 × 768 次元で 50 ms 以内をベンチで確認）
- [ ] 埋め込み近傍による重複クラスタ化（cos ≥ 0.93）
- [ ] 候補の expire（14 日）とパージ（90 日）ジョブ
- [ ] Prometheus メトリクス — 候補数・収集失敗数・埋め込みキュー長
- [ ] ユニットテスト（URL 正規化・重複判定・コサイン計算）

### 完了条件

- 7 日間連続で、毎日 100 件以上の新規候補が `recCandidates` に入る
- 重複率（`duplicateOfId` が埋まる割合）が妥当な範囲に収まっている（目視確認）
- プロフィール非依存ソースからの候補が全体の 20% 以上を占める
- D1 により、既存ブックマークから 20 件以上の未購読ドメインが発掘されている
- クロスリンガル整合の検証に合格している（下記）
- 埋め込み失敗率が 5% 未満
- ワーカー起因の `database is locked` が発生しない

### 手動作業

**埋め込みモデルのクロスリンガル整合を検証する**

- 目的: 日本語記事と英語記事が同じ空間に載っているかを、自分のデータで確認する。ここが崩れていると `cos(候補, プロフィール)` が話題ではなく言語を測る特徴量になり、設計の前提が壊れる
- 前提: Ollama に `embeddinggemma` と `qwen3-embedding:0.6b` を pull 済み。karakeep の pod から `/data/db.db` を読める（`kubectl exec` + node ワンライナー）
- 手順:
  1. `translationStatus='success'` のブックマークを 20 件抽出し、`htmlContent`（英語原文）と `translatedContent`（日本語訳）を取り出す
  2. 各記事について、原文と訳文の両方を `title: … | text: …` 形式に整形して埋め込む
  3. **検証 A** — 各記事で `cos(原文, その訳文)` を計算する。中央値 0.80 以上を合格とする
  4. 20 件を目視で 2 つの話題群 X / Y に分ける（各 10 件程度）
  5. **検証 B** — 話題 X の日本語訳が、話題 Y の日本語訳よりも、話題 X の英語原文に近いか。この関係が成り立つ記事の割合が 80% 以上を合格とする
  6. EmbeddingGemma と Qwen3-Embedding-0.6B を同じ 20 件で比較し、B のスコアが高い方を採用する
- 確認方法: 検証 A / B の両方が上記のしきい値を超えていること
- 失敗時の対処:
  - 両モデルとも B が 80% を切る場合、埋め込みだけで日英を横断させるのを諦め、**翻訳済み本文の側を埋め込む**方針に切り替える（翻訳パイプラインへの依存が増えるため次善策）
  - A だけが低い場合は翻訳品質の問題の可能性がある。`translationStatus` が success でも中身が壊れている記事を除外して再測定する

**RSS フィードの初期登録**

- 目的: 候補プールの供給源を確保する
- 前提: karakeep に管理者としてログイン済み
- 手順:
  1. 既存の morning briefing で使っている情報源を洗い出す
  2. 各サイトの feed URL を収集する（`/feed`, `/rss.xml`, `/atom.xml` の順で試す）
  3. `recSources` の seed スクリプトに登録する。うち 20% 以上に `profileIndependent=true` を立てる
  4. `pnpm --filter @karakeep/recommender run seed:sources` を実行
- 確認方法: 翌日 `recCandidates` にそのソース由来の候補が入っていること
- 失敗時の対処: 404 なら feed URL の探索をやり直す。パースエラーが続くソースは無効化して記録に残す

## Phase 1 — ヒューリスティック推薦と Briefing ページ

**目的**: 毎日 Briefing が出て、フィードバックが記録される状態を作る。**ここまでで実用になる**。学習はまだしない。

### 作業項目

- [ ] `heuristic-v1` スコアリング — プロフィール埋め込みとのコサイン + 鮮度減衰 + クラスタ重複ペナルティ
- [ ] `profile.ts` — 4 種プロフィールの初期構築。**既存ブックマークからブートストラップ**（`source='bootstrap'`）
  - お気に入り・ハイライト・読了率 60% 以上のブックマークを正例として長期プロフィールを作る
- [ ] k-means クラスタリングとクラスタラベル生成（LLM 呼び出しは 1 クラスタ 1 回のみ）
- [ ] 枠の混合（exploit / adjacent / uncertain / random）。`heuristic-v1` では uncertainty をクラスタの提示回数の逆数で代用する。trial 枠は Phase 1.5 で有効化する
- [ ] 多様性制約（同一クラスタ最大 3 件、同一ドメイン最大 2 件）
- [ ] `rankWorker` — 日次 Briefing 生成。**`exploit` / `adjacent` 枠は温度つき softmax の非復元抽出（`τ=0.15`）にし、propensity の実値を記録する**。argmax のままだとオフポリシー評価が原理的に不可能になるため、後付けできない
- [ ] 提示されなかった上位 100 件も `shown=false` で記録
- [ ] `packages/trpc/routers/recommender.ts` — Briefing 取得・フィードバック記録
- [ ] `/dashboard/briefing` ページ（カード一覧・4 操作・選定理由・興味の現在地パネル・過去日の遡り）
- [ ] **観測状態の記録** — `opened` イベント、離脱時の最深 `viewed` 順位、`observationState` の日次確定
- [ ] **`examined` 判定** — IntersectionObserver（50% 以上・1 秒以上）+ 通過証明（より下位のカードに `viewed` がある）
- [ ] **「興味なし」を 1 クリックにする**。理由入力は任意の追加操作に留める
- [ ] `unobserved` Briefing の上位 5 件を翌日 1 回だけ再提示するロジック（新しい impression として記録）
- [ ] 「保存」→ 既存ブックマーク作成フローへの接続と `bookmarkId` の紐づけ
- [ ] `rewardJoinWorker` — 遅延報酬の日次 join（観測窓 7 日）
- [ ] ベースライン計測用の A/B — 4 週間、20 件中 5 件を新着順ランダムに置き換えて記録
- [ ] Grafana ダッシュボード（**分母を `observed` × `examined` にした**クリック率・保存率、枠別の反応率、候補数、**Briefing 観測率**）

### 完了条件

- 毎朝 Briefing が自動生成される
- 4 週間分の impression とフィードバックが欠損なく記録されている
- propensity が全 impression に入っている
- `observationState` と `examined` が全 impression で確定している
- **Briefing 観測率が 60% 以上**（これを下回ると学習データが集まらない）
- ベースライン（新着順ランダム）のクリック率・保存率が算出できている
- 遅延報酬の join 率が 90% 以上

### 判断ゲート

- ヒューリスティックのクリック率がベースラインを**下回っている**場合、Phase 2 に進まずスコアリングの見直しに戻る。プロフィール構築か重複排除に問題がある可能性が高い
- **観測率が 50% を下回る場合、モデルの改善より先に「毎朝 Briefing を見る」運用のほうを直す**。通知・時間帯・件数を調整する。観測されない Briefing はどれだけ精度が高くても価値がない

## Phase 1.5 — ソース発見の基礎

**目的**: 候補プールを供給するドメインそのものを広げる。ここを飛ばすと、以降のすべての探索が「購読済みサイトの中での探索」に閉じる。

機械学習を一切必要とせず、既存データと公開 API だけで動く。**Phase 2 を待たずに実施する**。

### 作業項目

- [ ] `recDomains` / `recDomainDiscoveries` のライフサイクル実装
- [ ] `discoverWorker` の骨格（チャネルをプラグインとして追加できる形）
- [ ] **D2: 外部リンク抽出** — 正例ブックマークの `bookmarkLinks.htmlContent` から外部ドメインを抽出。被リンク数を元記事の報酬で重み付け。追加クロールなし
- [ ] **D3: フィード自動発見** — `<link rel="alternate">` 解決 + 慣例パス（`/feed`, `/rss.xml`, `/atom.xml`, `/index.xml`）のフォールバック
- [ ] **D4: アグリゲータのドメインサンプリング** — HN / Lobsters を記事源ではなくドメイン標本として使う
- [ ] 品質ゲート 4 段（ブロックリスト / 更新頻度 / 一次情報らしさ / LLM 分類 1 回きり）
- [ ] `trial` 枠の有効化（Briefing の 10%、1 日最大 2 件）
- [ ] ドメイン単位のベータ事後と Thompson Sampling による試用ドメイン選択
- [ ] **固定席（80）と押し出し方式**の昇格判定。満席時は最下位の現職を上回らないと着席できない
- [ ] **埋没判定** — 60 日間 1 度も Briefing に選ばれなかった購読ドメインを降格する
- [ ] **候補の日次取り込み上限 400 件** — ドメインの事後平均で配分し、候補プールのサイズをドメイン数から切り離す
- [ ] **取得頻度の 3 層化** — 上位 25% 毎日 / 中位 50% 3 日ごと / 下位 25% 週 1
- [ ] 昇格・降格の日次判定
- [ ] 「今日の新しい発見」UI ブロック（発見経路の説明つき、購読 / 却下の 1 クリック）
- [ ] クロールの礼儀（`robots.txt`、ドメインあたり 1 req/5s、連絡先入り User-Agent）
- [ ] メトリクス — 発見数・チャネル別昇格率・ドメイン集中度・新規ドメイン由来の保存率

### 完了条件

- D2 / D3 / D4 が毎日動き、週 5 件以上の新規ドメインが `screened` に上がる
- `trial` に常時 5〜10 ドメインが入っている
- 4 週間で 2 件以上のドメインが `subscribed` に昇格している
- 候補プールの日次流入が 400 件の上限内に収まり、ドメイン数が増えてもランキング所要時間が伸びていない
- 押し出しと埋没判定が実際に発火することを、席数を一時的に小さくして確認済み
- 品質ゲートで却下されたドメインをサンプル確認し、誤って良質サイトを落としていない
- 試用枠が原因で Briefing 観測率が下がっていない（下がっていたら試用件数を 1 日 1 件に減らす）

### 判断ゲート

試用ドメインの反応率が `random` 枠を**下回る**場合、品質ゲートが機能していない。ゲートを厳しくするか、発見チャネルの重み付けを見直す。無条件にドメインを増やさない。

## ログ蓄積期間（8〜12 週）

Phase 1 完了後、モデル学習に必要なデータが貯まるまで待つ。この間は Phase 4 を並行して進められる。

**必要データ量の目安**

| 条件 | しきい値 | 1 日 20 件提示・観測率 70% での到達時期 |
|---|---|---|
| `examined` impression 総数 | 2,000 件 | 約 20 週 |
| 正例（strong_positive） | 100 件 | クリック率 25%・保存率 8% なら約 13 週 |
| 学習ペア総数 | 3,000 組 | 正例が揃えば自動的に満たされる |
| `observed` な Briefing 日数 | 60 日 | 約 13 週 |

**観測率を掛けた分だけ到達が遅れる**点に注意する。`unobserved` な Briefing は学習に使わないため、Briefing を見ない日が多いほど Phase 2 が後ろにずれる。観測率は Phase 1 の完了条件に入れてある。

ペア数は正例数から自動的に増えるが、**独立な情報は正例の絶対数で決まる**。ペアが 3,000 組あっても正例が 30 件しかなければ学習は成立しない。しきい値は正例数を主、ペア数を従として判定する。

ブートストラップした既存ブックマークは正例のカウントに含めてよいが、`examined` impression の分母には含めない（提示されていないため）。またペアの相手（`examined` 未操作）が存在しないので、ペアワイズ学習には使えない。**ブートストラップはプロフィール構築専用**とする。

この期間中に週次で確認すること:

- Briefing 観測率（下がってきたら件数を減らす、時間帯を変える）
- 枠別の反応率（exploit / uncertain / trial / random の差）
- 探索枠から新しい選好クラスタが生まれているか
- 新規ドメイン由来の保存率とドメイン集中度
- 「興味なし」の件数と理由の分布（週 3 件未満なら押す習慣がついていない。UI で軽く促す）

## Phase 2 — ペアワイズ学習

**目的**: ログから学習する。ヒューリスティックを実データで上回る。**「押されなかったこと」を負例にしない**定式化で組む。

### 作業項目

- [ ] `features.ts` — 20 特徴量の抽出（ドメインのベータ事後を含む）。特徴量スキーマのバージョニング
- [ ] `pairs.ts` — 同一 Briefing 内のペア生成。`observed` × `examined` でフィルタし、`P_b × N_b` を作る。**重みは日ごとに `1/|N_b|` で正規化する**
- [ ] **Briefing 内で一定の特徴量を除去または交互作用化する**（曜日・スロット・切片は差分で消えるため同定不能）
- [ ] `model/logreg.ts` — 差分ベクトル `x⁺ − x⁻` に対する L2 正則化ロジスティック回帰。バッチ勾配降下（数千組なので全件バッチで十分）
- [ ] ペア重みの実装（strong_positive 1.0 / weak_positive 0.3 / dismissed 1.5）
- [ ] ポジションバイアス補正（学習時のみ `rank` を特徴に含め、推論時は 1 固定）
- [ ] 推論時は差分ではなく `w·x` をそのままスコアとして使う（ペアワイズ学習の重みはランキング関数として直接使える）
- [ ] `trainWorker` — 日次再学習。昇格条件を満たさない場合は何もせず理由をログに残す
- [ ] 時系列分割による評価（直近 2 週間をテストに）— **ペア正解率**と、Briefing 単位の NDCG@20 / 上位 5 件の保存率
- [ ] シャドー評価 — 新モデルを 7 日間、予測のみ記録して比較
- [ ] `recModels` へのバージョン保存とロールバック手順
- [ ] 特徴量寄与の可視化（`explain_article_score` の下地）

### 完了条件

- `logreg-v1` のペア正解率と NDCG@20 がシャドー評価で `heuristic-v1` を上回る
- 上位 20 件の保存率がヒューリスティックを上回る
- 学習ジョブが 60 秒以内に完了する
- ロールバック手順が実際に動作することを確認済み

### 判断ゲート

シャドー評価で上回らない場合、**昇格させずに Phase 3 を飛ばして待つ**。データ不足が原因なのか、特徴量が悪いのかを切り分ける。切り分けの順序:

1. 特徴量ごとの単変量ペア正解率を見て、明らかに効いていない特徴を落とす
2. 正則化の強さを調整する
3. ペアの負側（`examined` 未操作）に偽の負例が混ざっていないか確認する。`examined` の判定が甘いと、見えていない記事が比較対象に入ってしまう
4. それでも改善しないなら、データ量が足りないと判断してさらに 4 週間待つ

無理にモデルを昇格させないこと。ヒューリスティックのまま運用しても実用上の損失は小さい。

## Phase 3 — 探索制御・潜在プロフィール・ソース発見の拡張

**目的**: 不確実性を推定し、Thompson Sampling で探索を制御する。同時に、発見チャネルを潜在プロフィール駆動のものへ広げる。

### 作業項目

- [ ] `model/logreg.ts` にラプラス近似による事後共分散を追加（20 次元なので完全共分散を持てる）
- [ ] Thompson Sampling — 重みを事後分布からサンプリングしてスコアを算出
- [ ] `uncertainty` をヒューリスティック代用から事後標準偏差に置き換え
- [ ] 探索率の自動調整 — 直近の探索枠の当たり率に応じて 5〜25% の範囲で動かす
- [ ] 潜在クラスタの可視化強化 — 「興味の現在地」パネルに新興クラスタとトレンドを表示
- [ ] 否定プロフィールの精緻化 — 「興味なし」の理由別に扱いを変える（テーマ違いのみを否定プロフィールに反映し、情報源が弱いはドメインのベータ事後に反映）
- [ ] クラスタ選好のベータ分布平滑化

## Phase 5 — 収集戦略の最適化とオフポリシー評価

**目的**: 収集段階を改善対象に含める。ここまで凍結していたのは、推薦モデルと同時に動かすと原因分析ができなくなるため。

### 作業項目

- [ ] 収集設定のパラメータ化
  - 探索率 / 情報源の多様性 / 一次情報優先度 / 新規トピック比率 / 重複許容度 / 専門性 / 速報性
- [ ] 収集設定のバージョン管理と、候補への設定 ID の紐づけ
- [ ] 設定別の下流指標（その設定で集めた候補の採用率・保存率）の集計
- [ ] **手動 A/B から開始** — 2 設定を隔日で切り替え、4 週間比較する。自動最適化はここでは行わない
- [ ] オフポリシー評価（IPS / SNIPS）の実装。過去ログから新ランキングポリシーを評価する
- [ ] `avoid_patterns` の実装（製品発表の転載、内容の薄いまとめ記事）— LLM による候補フィルタ、ただし収集時 1 回のみ
- [ ] **D9: LLM 検索エージェント** — 未開拓トピックの Web 探索。記事の収集だけでなく**新規ドメインの発見器**として使う。低頻度（週次）に留める
- [ ] 収集設定のバンディット化は、オフポリシー評価の妥当性が確認できてから

### 完了条件

- 収集設定の違いが下流指標に与える影響を定量的に示せる
- オフポリシー評価の推定値と、実際に運用した際の実測値が近い（推定の妥当性が確認できる）

### 判断ゲート

収集設定を**バンディットの行動として自動最適化するのは、オフポリシー評価が信頼できることを確認してから**。それまでは手動 A/B に留める。収集と推薦の両方が自動で動くと、性能変化の帰属先が分からなくなる。

## 中止・巻き戻しの基準

以下に該当したら、そのフェーズを巻き戻して下位モデルに戻す。

- モデル昇格後 2 週間で、保存率が昇格前を 20% 以上下回った
- 探索枠のクリック率が 4 週間連続で 5% を下回った（探索が機能していない）
- 候補プールのクラスタ数が 4 週間連続で減少した（多様性が失われている＝フィードバックループの兆候）
- **ドメイン集中度が 8 週間連続で上昇した**（ソース探索が死んでいる）
- **購読ドメインの下位四分位が 120 日以内に `examined` 20 件へ到達できていない** — 席が多すぎて降格判定が働かない状態。席数を減らす
- **Briefing 観測率が 4 週間連続で 50% を下回った** — 学習を停止し、UI と運用の見直しに戻る。この状態で溜まるログは偽の負例を含むため、使わない
- **`dismissed` が 4 週間連続で週 3 件未満** — 明示的な負例が枯れている。UI 側で促す
- Briefing 生成が週 2 回以上失敗した
